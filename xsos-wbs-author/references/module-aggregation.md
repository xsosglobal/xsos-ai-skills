# 模块聚合：工作包怎么组织，怎么不重复

> 决策人：顾昊，2026-09-09。本文件是建 WBS 包时的方法论规范，`add_work_package.py`
> 的重复扫描按它设计，评审建包时按它判断。

## 为什么要有这份规范

起因是 `WP-FE-162` 重复了 `WP-FE-147/148/149`——同一件事（个人中心迁移）在两个
时期被各立了一套包，立项时没人发现。查下来这不是偶发的粗心，是建模本身的问题：

**把工作包当成「一次工作」来立，重复是结构性的、必然的。**

- 「工作」是动词，一次性的：迁移、联调、补页、修接口。做完就结束。
- 系统是由名词组成的，持久的：个人中心、文件服务、打印机。它们一直在，被反复改。
- 用一次性的动作去覆盖持久的东西 → 同一个模块被多次「工作」触及 → 每次立一个新包
  → 它们平级漂着、看不出是一回事 → 重复。

这正是经典 WBS 方法论的核心原则被违反了：**WBS 应当按「可交付成果」分解，不是按
「任务」分解**（deliverable-oriented, not task-oriented）。

## 分层模型

```
模块（持久骨架）
  └── 工作包（可独立验收、有明确交付范围和结束条件的交付单元）
        └── 工作项（迁移 / 接口开发 / 联调 / 测试 —— 包内部的活，不各自立包）
```

**长期存在的是模块；工作包仍然要有明确的交付范围和结束条件**（不是漂浮的动作，
而是一个能独立验收的交付物）；迁移、接口开发、联调、测试是这些包**里面的工作项**。

例：「个人中心」模块下聚合——
- **资料与头像管理**：一个可独立验收的工作包。
- **修改密码**：另一个工作包。
- **登录设备管理**：后续新增能力，再建工作包。

每个包各有自己的交付范围与验收；「迁移它」「联调它」「测试它」是包内的工作项，
不是三个平级的包。

## 五条规则

### 1. 建包时关联模块（交付对象）+ 项目

每个工作包声明它作用于哪个**模块/交付对象**，同时关联**实际项目**。一个包可以
涉及多个项目。模块是聚合维度，项目是归属维度，两者都记。

### 2. 先展示相关已有包，再判断是否重复

建包前，工具先列出同模块/同业务词的已有包。**但同一模块不代表同一需求**——
必须打开这些包，**比较它们的【交付范围(scope)】和【验收标准(acceptance)】**，
不能望文生义。`add_work_package.py` 的重复扫描做「展示」，判断由人做。

### 3. 同交付范围的补充 → 改原包；独立新能力 → 新建包

- 交付范围与已有包重叠 = 同一交付物的补充 → **修改原包并保留变更记录**（改号或
  改表，走 CHANGELOG），不新立。
- 范围不同、是这个模块的独立新能力 → **新建包**。

判据是「交付范围是否重叠」，不是「是否同模块」。

### 4. depends_on 和模块关联，分别保留

- `depends_on` 表达**先后依赖**（A 做完 B 才能做）。
- **模块关联**负责**聚合**（同一个模块的所有包聚在一起看）。

两者是不同维度，不要混用——不要把「属于同一模块」硬塞进 `depends_on`，那会让
依赖图变脏；也不要用 `depends_on` 代替模块聚合。

### 5. 旧包先补归属，不强行合并

已存在的几百个包不推倒重来。渐进迁移：**旧包先补上模块归属**（加 module 字段），
**不强行合并**。这样既能看清一个模块的完整建设过程，又保留每次交付和版本的边界。

## 字段设计（schema 演进，待逐步落地）

给工作包增加两个维度字段。它们是**独立于 `depends_on`** 的新维度：

| 字段 | 含义 | 例 |
|---|---|---|
| `module` | 所属模块/交付对象（聚合维度，一个包一个模块） | `个人中心` |
| `projects` | 关联的实际项目（归属维度，可多个） | `["Portal迁移", "四端统一登录"]` |

落地方式（渐进，不一次改完 26 个仓库）：

1. `add_work_package.py` 的 spec 接受 `module`（必填）与 `projects`（可选，数组）。
2. `02-wbs.md` 表增加 `module` / `projects` 两列；仓库尚未加列时，脚本提示「建议加列」
   而不是报错，保证渐进兼容。
3. 重复扫描优先按 `module` 聚合展示同模块的包（比纯业务词更准）。
4. 存量包按第 5 条逐步补 `module`，不强行合并。

在字段全面落地前，`add_work_package.py` 已用业务词 n-gram 做「近似同模块」的重复
提示（见 `scan_similar_packages`）——那是字段化之前的过渡手段。

## 一句话

**模块是持久的骨架，工作包是骨架上可独立验收的交付单元，工作项是包里的活。
建包先看同模块已有包、比交付范围和验收：范围重叠就改原包，独立新能力才新建。**
